# 层次 4：测试与验证纪律

## 1. 核心命题：测试通过 ≠ 根因确认

这是本层次唯一需要先立住的命题，其余都是它的推论。

**C23 —— Wang, Pradel & Liu, *Are “Solved Issues” in SWE-bench Really Solved Correctly? An Empirical Study*, arXiv:2503.15223v2（DOI 10.1145/3744916.3764576）**
（`research/swe-bench-solved-issues-really-solved.pdf`）

摘要逐字：

> …testing is rarely exhaustive, **a patch may pass the tests but nevertheless fail to match the developers' expectations**. Unfortunately, it is currently unclear to what extent evaluations performed with SWE-bench suffer from such **plausible but incorrect patches**. This paper presents an in-depth empirical study of the correctness of plausible patches generated by three state-of-the-art issue-solving tools (CodeStory, LearnByInteract, and OpenHands) evaluated on SWE-bench …

两个量化结论：

| 数值 | 精确含义 |
|---|---|
| **7.8%** | 所有被计为「correct」的 patch 中，有 7.8% **无法通过开发者编写的测试套件** |
| **29.6%** | 可信 patch 中，有 29.6% 与 ground-truth patch **行为不同** |

论文摘要的定性表述：`Our findings reveal critical weaknesses in SWE-bench's patch validation mechanism`。

**这对多仓问题单修复的三条直接含义：**

1. 任何「测试全绿 → 判定修复成功」的流程，都必须标注其**误判率下界约为 7.8%**；在多仓 + 无开发者测试的条件下这个下界只会更高。
2. 29.6% 说明「通过测试」与「行为正确」之间有近三成的缺口，必须有独立于测试的验证通道。
3. 反过来，这也说明**不能把 7.8% 直接当成 agent 的错误率**——其中相当部分是 benchmark 验证机制本身的缺陷。这是两个不同的失效源，必须分开度量。

## 2. 差分验证：PatchDiff 与「没有 ground truth 怎么办」

该研究提出的技术（C24）：

> a technique for **differential patch testing**, called PatchDiff, which automatically exposes behavioral discrepancies between two patches.

关键洞察（**结构推论**）：PatchDiff 比较的是**两个 patch 之间的行为差异**。因此它不需要真实修复（ground truth）——只需在多个输入上运行「程序 + patch A」与「程序 + patch B」，比较可观测输出差异。

推论出的三层差分验证（**设计判断**）：

| 层 | 比较对象 | 用途 |
|---|---|---|
| D1 | 原程序 vs 打补丁后的程序（多输入域） | 检测「改坏」与「没改对」的基线 |
| D2 | patch A vs patch B（候选冲突时） | 裁决候选，或直接复用 PatchDiff 思路 |
| D3 | 不同 metamorphic 变换下的程序（见 §3） | 无 oracle 时合成判别 |

这与既有的复现门禁互补：复现门禁回答「原始失败是否消失」，差分验证回答「其他行为是否保持」。

## 3. Metamorphic Testing：没有测试时的合成 oracle

**C45 —— Chen, Kuo, Liu, Poon, Towey, Tse & Zhou, *Metamorphic Testing: A Review of Challenges and Opportunities*, ACM Computing Surveys 51(1), Article 4, 27 pages, 2018（DOI 10.1145/3143561）**
（`research/chen-csur2018-metamorphic-testing.pdf`）

论文引用的一项实证研究给出的数字：

> For each of the six subject programs in the study, **MT only required an average of three to six diverse MRs to reveal at least 90% of the faults that could be detected by an oracle**.

即：**每程序 3–6 条 diverse metamorphic relation 即可达到 oracle 可检测故障的 90% 以上。**

论文自身对 MT 与无 oracle 回归测试（RT）的关系给出清晰界定（C46）：

> The base program can then be used as the oracle. **RT with the oracle provides the upper bound** of the fault detection effectiveness. **RT without the oracle provides the lower bound** — in which case we can only detect faults related to program crashes, such as segmentation faults. **It is usually reported that MT always detects more faults than RT without the oracle.**

同文还指出 MT 与 error trapping 互补。

**对多仓问题单修复的意义（结构推论）：** 结合 C34（真实 issue 只有 5.5% 带可执行 test case），metamorphic relation 是**唯一可规模化合成 oracle 的手段**。多仓场景下常见的 MR 家族：

| MR | 适用 |
|---|---|
| 输入顺序不变 | 批处理、聚合接口 |
| 单位/格式等价变换 | 序列化、时间格式、数值精度 |
| 幂等性 | 重复请求、重复消息 |
| 集合划分不变 | 分页、批处理切分 |
| 缓存前后等价 | 引入/绕过缓存层 |
| 跨仓接口等价 | 上下游 mock vs 真实 |

注意 MR 需要**领域知识**，不能自动生成——这是它最大的落地成本。

## 4. Flaky Test：判定噪声的地板

**C42、C43、C44 —— Luo, Hariri, Eloussi & Marinov, *An Empirical Analysis of Flaky Tests*, FSE 2014, pp.643–653（DOI 10.1145/2635868.2635920）**
（`research/luo-fse2014-flaky-tests.pdf`）

工业规模数据（C42，§1 引言）：

> the TAP system at Google had **1.6M test failures on average each day in the past 15 months**, and **73K out of 1.6M (4.56%) test failures were caused by flaky tests**.

论文对通行折中的否定（C43，§1）：

> The current approaches to combat flaky tests are rather unsatisfactory. The most common approach is to **run a flaky test multiple times, and if it passes in any run, declare it passing, even if it fails in several other runs**.

研究规模：51 个开源项目中 201 个疑似修复 flaky test 的 commit。

根因分类（C44，论文原文）：

> **Async Wait** flaky tests use sleep or waitFor with a time delay to enforce ordering. Their flaky failures **can be simply manifested by changing the time delay**.

另一个被点名的类别是 order dependence（测试顺序依赖）。

**工程结论（设计判断 + 观测事实）：**

| 判定 | 正确形式 | 依据 |
|---|---|---|
| 立案 | 固定 revision + 固定环境下，**N 次连续全红** | C42 的 4.56% 噪声地板 |
| 排除 | 先做**确定性/时序稳定性检查**（改时间延迟、并行度、随机种子）再谈根因 | C44 |
| ❌ 禁止 | 「重跑 N 次，任一次通过即算通过」 | C43 明确指出这是不令人满意的做法 |

多仓放大效应：跨 N 个仓的测试套件整体失败概率随 flaky 事件累积，「一次跑通全栈」的偶然性不可忽略。

## 5. Mutation Testing：作为压力源，而非门禁

**C47 —— Papadakis, Kintis, Zhang, Jia, Le Traon & Harman, *Mutation Testing Advances: An Analysis and Survey*, Advances in Computers 112:275–378, 2019（DOI 10.1016/bs.adcom.2018.03.015）**
（`research/papadakis-advcom2019-mutation-survey.pdf`，153 页）

综述自身的定位判断：

> Mutation has reached a **maturity phase** and gradually gains popularity both in academia and in industry. This chapter presents a survey of recent advances, over the past decade … and sets out the **challenges and open problems** for the future development of the method.

其中关于变异分数的一项经验发现（论文表内条目）：

> mutation score and test suite size correlate with fault detection rates, but often **the individual (and joint) correlations are weak**.

综述规模：涵盖 25 篇基础性论文、34 篇工具论文、217 篇仅用于测试充分性评估的论文。

**结论：** 变异测试的两个经典难题（等价变异体 equivalent mutants、跨层效率）尚未解决；且变异分数与故障检出率的相关性常常很弱。

**工程结论（设计判断）：** 变异分数**不能**当作「测试足以确认根因」的证据。它正确的用法是**压力源**——用定向变异去攻击验证层，暴露验证层的漏洞（等价变异体不重要，重要的是「引入变异后验证层仍全绿」的那部分，这直接等价于 patch overfitting 的检出能力）。

对 APR 而言这有一层额外价值：把测试套件与 patch 一起变异，可以直接量化「patch 究竟修了几类缺陷」。

## 2. SWE-bench：难度的原始锚点

**C25**（`arxiv-2310.06770.pdf`，ICLR 2024 会议版）：

> an evaluation framework consisting of **2,294 software engineering problems** drawn from real GitHub issues and corresponding pull requests across **12 popular Python repositories** … The best-performing model, **Claude 2, is able to solve a mere 1.96%** of the issues.

**C26**（§2.1 + 摘要）：

> We highlight that the codebases are large with **thousands of files**, and the reference pull requests **often make changes to multiple files at once**.

摘要另有一句给出任务本质：

> Resolving issues in SWE-bench frequently requires **understanding and coordinating changes across multiple functions, classes, and even files simultaneously**, calling for models to interact with execution environments, process extremely long contexts and perform complex reasoning.

**含义：** 多文件改动是任务的**内禀分布**，不是异常。「patch 只动一个文件」不应作为默认期望；SWE-bench Lite 的筛选标准恰好是「more self-contained, with a focus on evaluating functional bug fixes」——所以 Lite 上的成功率系统性高于 full。

## 4. 多文件显著掉点（量化）

**C29 —— Rashid, Bock, Zhuang, Buchholz, Esler, Valentin, Franceschi, et al., *SWE-PolyBench*, arXiv:2504.08703v3**
（`arxiv-2504.08703.pdf`）

§5.3 结果分析逐字：

> Table 5 reveals how performance degrades with increasing task complexity, where **all methods reach their maximal pass rate on single file edits**. For tasks that require more file edits, a notable performance decrease can be noticed with instances requiring **edits of three or more files, success rates start falling below ten percent**. However, it's important to note that **without human annotation of test quality, we cannot definitively attribute this drop solely to task complexity**. The specificity of the tests may also be a contributing factor.

三点读数：

1. **单文件编辑是所有方法的性能峰值**。
2. **3 文件及以上：成功率跌破 10%。**
3. 论文自己加了限定：**不能把掉点全归因于任务复杂度，测试特异性也可能是成因。** 这条限定必须保留——否则会得出「多文件任务不可做」的错误结论。

对多仓的含义：**掉点有至少两个可分离成因（任务复杂度 / 测试特异性 / 定位精度）**。本项目的消融必须能分离这三者，否则无法判断投入方向。

## 5. Patch token 长度阈值：未找到一手证据

调研提纲要求的「patch token 长度阈值」结论，本轮**未取得一手出处**。

- Multi-SWE-bench 中有一组相关但**不同**的数字（C38）：同一 issue 被改动的**行数**（Medium 平均 427.5 行、Hard 平均 904.2 行 vs Easy 494.5 行，表 3 附近）与难度相关；
- AutoCodeRover Table 2 给出的是**总 token 消耗**与成功率的关系（C14），不是「patch 超过某长度即失败」的阈值。

**结论（标为待验证假设）：** 「patch 长度超过某阈值即导致成功率显著下降」目前只有**间接证据**（多文件掉点 C29 + issue 类型分布 C38），**没有直接的一手阈值数字**。不作为论断写入正文结论。

### 6.2 主张二：长度无一致关系（Multi-SWE-bench）

**C30 —— Multi-SWE-bench, arXiv:2504.02605v1, §6.2.2 Characteristics of Issue Description**

论文先把长度分布说清楚：

> Fig. 9 illustrates the distribution of issue lengths (in tokens) in Multi-SWE-bench, which follows a **power law**, with the majority of issues being **under 1,000 tokens**. To explore the effect of description length, the issues are categorized into 5 intervals: **<100, 100-400, 400-700, 700-1000, and >1000 tokens**.

结论逐字：

> **As shown in Fig. 10, there is no consistent relationship between issue description length and resolved rate.** For example, in Python, issues with longer descriptions tend to have lower resolved rates, whereas in Go, longer descriptions are associated with higher rates. This discrepancy arises from two potential types of long issue descriptions: **(1) detailed issues with precise issue position indications and resolving steps**, and **(2) complex issues that require extended descriptions to explain**.

### 6.3 矛盾的调和（结构推论）

| 维度 | Khatib 2026 | Multi-SWE-bench | 综合判断 |
|---|---|---|---|
| 数据 | 单仓（SWE-bench 类）n=433 | 多语言 7 语言 1,632 实例 | 样本与语言不同 |
| 方法 | 分层回归 + OR，含控制变量 | 分箱后的定性描述，无显著性检验 | Multi-SWE-bench 未给统计检验，结论强度较弱 |
| 结论 | log 长度 OR=0.49，显著负向 | 「无一致关系」 | **方向可冲突，但两者都不支持「长=好」** |

**可操作的共识（结构推论）：** 长 issue 单有两种成因——「详尽且已定位」与「复杂难解」——这正是 Multi-SWE-bench 给出的机制解释。Khatib 的 OR=0.49 在控制其他特征后仍显著，说明**长度本身携带的是「复杂/难解」的信号**。

因此本项目的 issue 单治理动作应是**按信息结构而非长度**：

```
必填（OR ≥ 2.3）：复现脚本、被改文件路径、环境信息、修复建议
可选：仓库代码片段、错误消息、定位到函数
不应作为质量代理：总长度、自然语言复现步骤、可读性、堆栈
```

**且必须承认这是跨数据集冲突的弱共识，不能写成硬规则。**

> …we additionally form an internal quality assessment team of **14 experienced engineers**. After rigorous manual verification, a total of **1,632 high-quality instances** are retained as the final Multi-SWE-bench, filtered by annotation criteria …: Q2.1=0 & Q3.1∈{2,3} & Q4.1∈{2,3}.

## 8. 其他 benchmark 的独立变量

**C39 —— SWE-bench Multimodal（arXiv:2410.03859v1）**

> SWE-bench M is a dataset of **619 multimodal, JavaScript task instances** collected from **17 open-source GitHub repositories**.
>
> （对比）only **5.6%** of SWE-bench tasks contain an image.
>
> （人工核验）we find that for **83.5%** of task instances, **images are necessary** for solving the corresponding issue.
>
> （结论）We discover that existing systems perform **significantly worse on SWE-bench M than they do on SWE-bench**, due in large part to the challenges of visual problem solving and JavaScript's diverse development…

含义：视觉类 issue 是**独立能力轴**，纯文本修复流程在其上不可用；不应混入统一成功率分母。

**C40 —— SWE-Lancer（arXiv:2502.12115v4）**

> a benchmark of **over 1,400 freelance software engineering tasks from Upwork, valued at $1 million USD** total in real-world payouts. SWE-Lancer encompasses both independent engineering tasks — ranging from **$50 bug fixes to $32,000 feature implementations** — and managerial tasks …
>
> Most tasks (**88% of IC SWE tasks and 94% of SWE Management tasks are bug fixes**).
>
> （难度）The average task in the Diamond set takes **26 days** to resolve on Github and has **47 comments**.

含义：**真实 issue 单的主要形态确实是 bug fix**（与 C11 的 iFixR 结论一致：问题单驱动修复是真实主线任务）；但任务体量远大于 SWE-bench，真实场景成功率预期要下调一个档。

**C41 —— Terminal-Bench（arXiv:2601.11868v1）**

> we present **Terminal-Bench 2.0**: a carefully curated hard benchmark composed of **89 tasks** in computer terminal environments inspired by problems from real workflows. Each task features a **unique environment, human-written solution, and comprehensive tests for verification**. We show that frontier models and agents score **less than 65%** on the benchmark and … smaller models scoring around **15%**.

其中「人类难度预测 vs 实测难度」的相关系数（Figure 7）：

> of all tasks rated **hard by humans, 93.3% were also empirically hard** for models, 3.3% were medium, and 3.3% were easy. Overall correlation: **r = 0.436, p < 0.001**.

含义：**「人觉得难」不是有效的难度预测器（r=0.436）。** 难度必须用实测通过率定义，人工标注只能作弱先验。
