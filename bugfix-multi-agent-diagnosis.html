根因诊断

当前失败的证据化原因

以下发现由工作流定义直接支持；不把缺失 trace 推定为模型幻觉或工具故障。

P0

停止条件与下游前置条件矛盾

三轮皆为 NEEDS_DYNAMIC_INVESTIGATION，下游却假定存在 confirmed_root_cause。固定轮数把未收敛状态伪装成流程完成，导致修复基于未确认根因。

P0

没有最小区分实验契约

审查产物只有 verdict + evidence_gaps，没有要求候选假设、可观察预测、反证标准、执行命令或实验结果。“需要动态调查”不是可执行的诊断任务。

P0

重复调查未声明新信息条件

Round 2、3 都调查同一 CodeMate-WebView 且均未收敛；输入未描述二者不同的触发路径、观测指标或 falsifier。重复调用不必然增加证据独立性或信息增益。

P1

审查成为关键路径瓶颈

Round 1 reviewer 64m，超过最长 investigator 的 60.6m。自由文本报告迫使审查者从 Markdown 重建证据结构，与“审查是轻量收敛器”的预期相悖。

P1

状态所有权不单一

team-leader 与 hypothesis-manager 均可更新 belief-state.json；reviewer ↔ investigator 又有旁路 P2P。无版本号、写入租约或事件日志，无法证明决策使用同一证据快照。

P1

缺少可审计的端到端 trace

Phase 时长口径冲突，且无 token、工具调用、重试、队列、cache、测试结果字段。无法区分“模型慢”“工具慢”“排队”“上下文膨胀”。

以下事项在当前材料中均无证据，必须以 trace/测试工件/人工标注验证：模型是否幻觉、某仓库是否本来无 bug、动态工具是否失败、reviewer 是否读错报告、belief-state 是否发生竞争写入、或某 Agent prompt 是否不充分。

实现漂移告警

Demystifying Evals

目标架构

以诊断闭环替代报告闭环

将 Phase 3 从“出报告、审报告、再出报告”的文档流水线，改造为“可复现 → 候选根因账本 → 最小区分实验 → 证据门禁”的闭环。

Issue / 日志
→
可复现门禁失败命令 + 环境指纹
→
范围定位变更 · 调用链 · 所有权图
→
根因账本候选假设 + 预测 + 反证
实验调度器选择最高信息增益实验
→
受限 investigator运行 · trace · 最小探针
→
证据校验器schema · 可重现性 · 冲突检查
↻
确认门禁或升级人工

证据契约：从自由报告改为结构化 schema

每一次 investigation 必须产生结构化证据单元；自由文本只作为 notes 附件。

字段说明
hypothesis_id绑定的候选假设 ID
claim断言描述
prediction可观察预测
falsifier反证条件：若 X 发生则拒绝该假设
method执行命令 + 环境摘要
observation可引用的 trace、日志行或测试输出
supports / contradicts受支持/被否定的候选假设 ID 列表
reproducible布尔值；artifact_refs 引用 hash
next_experiment仅当仍不能区分存活假设时填写

证据校验器应拒绝：没有预测、没有观测、无可重现命令、或只含主观 confidence 的结果。

控制面：一个状态写入者 + 不可变事件日志

case.json

版本、状态机阶段、预算、最后一次决策；由 case-controller 单写。

evidence.ndjson

不可变事件，含 artifact hash、生成 Agent、命令、时间、仓库 revision。

hypotheses.json

由事件流物化；每个假设有 prior、支持/反驳证据、预测与 next experiment。

decision.json

每次 continue / confirm / escalate 的 snapshot hash、规则命中项与预算消耗。

P2P 消息可保留，但只能创建“补证请求/答复事件”，不能直接改变假设权重或通过确认门禁。

停止规则

确认根因的三道门

不能以“跑了三轮”或 reviewer 文字判定替代因果验证。

1

现象可复现

原始失败在固定 revision 与环境中可复现。

2

因果链成立

观测满足该假设预测，并排除至少一个强竞争候选。

3

干预可验证

最小 patch 或开关按预测改变失败现象，独立验证未发现明显回归。

Reproduce→ Scope→ Experiment↻ Confirmed→ Repair→ Validate
Escalated ← 预算耗尽 / 无可区分实验 / 不可复现 / 验证失败
任一条件未满足 → UNRESOLVED / ESCALATED，不得写入 confirmed_root_cause。固定 N 轮是成本上限，不是“视为确认”的条件。

演进计划

分阶段路线图

第 1 周 · 可观测

先让失败可见

  • 统一 span 与时间口径（wall-clock / active / queue / tool）
  • 收集 20–50 个冻结脱敏 case
  • 建立 4 个 trace grader（复现、反证、区分度、状态一致性）
第 2–3 周 · 实验协议

让调查产生信息增量

  • 用 evidence schema 取代自由报告作为决策输入
  • 创建 case-controller 单写 + append-only evidence log
  • reviewer：一次结构化判定 + 一次基于 schema 缺失的补证，超限升级
  • 默认任务改为“区分 H-x 与 H-y 的实验”
第 4–6 周 · 消融

用实验证明多 Agent 是否值得

  • S0：单 Agent 定位→修复→验证（基线）
  • S1：单 case owner + 结构化工具/证据协议
  • M1：S1 + 仅独立实验并发
  • M2：当前 reviewer + P2P + 三轮（遗留对照）

立即执行

立即可落地的决策

1. 暂停“固定三轮后进入修复”

改为确认门禁或 ESCALATED。消除错误修复风险的第一优先级。

2. 下一次只运行一个 case

先完成复现、候选账本和一个最小区分实验；不要先并行四个宽泛 investigator。

3. 审查输出改为可机检 decision

必须列出存活假设、已满足/缺失证据和唯一下一实验；无下一实验即升级。

4. 补全 trace 后再讨论模型/prompt/数量

当前时间统计不足以支持模型、prompt 或 Agent 数量方面的归因。

5. 以 S0/S1/M1/M2 消融决定长期拓扑

多 Agent 是待验证的性能优化，不应作为定位正确性的前提。
